1. The Problem: Super-Linear Build Time

When building larger cities, the build time scaled super-linearly. A 100-block city took ~6 seconds, but a 500-block city took over 2 minutes. The goal was to identify and eliminate the bottlenecks.

Measured Build Times (Before Optimization)

500 blocks
124s
1000 blocks (est.)
~360s+ (Unity froze)
Why Super-Linear?

5x the blocks should mean 5x the time (linear scaling). Instead, 500 blocks took 20x longer than 100 blocks. This indicated compounding bottlenecks — not just "more work" but "work that gets harder as you add more."

3. Optimization #1: Parallel Terrain Generation

The Problem

Terrain generation iterated through every city block sequentially on the main thread, computing voxel data for roads, sidewalks, and ground tiles one chunk at a time.

Before — Sequential (Single Thread)
Main Thread Block 1 → Block 2 → Block 3 → ... → Block 500
→
Each block: ~12ms math
500 × 12ms = ~6,000ms

One CPU core does all the work while the other 7-15 cores sit idle.

After — Parallel.For (All Cores)
Main Thread Pre-compute metadata
bounds, dims, origins
→
Worker Thread 1 Block 1
Worker Thread 2 Block 2
Worker N Block N
→
Main Thread Assemble results
500 blocks in 11ms

How It Works

// Phase 1: Pre-compute all chunk metadata on main thread (no Unity API needed) var meta = new ChunkMeta[blockCount]; for (int i = 0; i < blockCount; i++) meta[i] = ComputeChunkMeta(row[i], col[i], ...); // Phase 2: Allocate arrays upfront var dataArray = new uint[blockCount][]; // Phase 3: Fill voxel data in parallel — pure math, no Unity API calls Parallel.For(0, blockCount, i => { dataArray[i] = new uint[meta[i].w * meta[i].h * meta[i].d]; FillRoadStrip(dataArray[i], ...); // pure math FillGroundTile(dataArray[i], ...); // pure math }); // Phase 4: Assemble TerrainChunk list on main thread for (int i = 0; i < blockCount; i++) chunks.Add(new TerrainChunk { data = dataArray[i], ... });
Result: 6,000ms → 11ms (545x faster)

The math was never the real problem — it was doing it one-at-a-time on a single core. Spreading it across all CPU cores made it nearly instant.

4. Optimization #2: Parallel Building File Pre-Load

The Problem

Each building is stored as a .stasset binary file. The old code read these files one at a time during the building placement loop — disk I/O is inherently slow and sequential reads waste time.

Before — Sequential File Reads
Main Thread Read file 1 → Parse → Pack → Read file 2 → Parse → Pack → ...
→
46 unique files × (read + parse + pack)
~60,000ms total
After — Parallel Pre-Load
Thread 1 Read+Parse file_1.stasset
Thread 2 Read+Parse file_2.stasset
Thread N Read+Parse file_N.stasset
→
Main Thread Merge into cache (thread-safe Dictionary)
46 files in 11ms
Result: ~60,000ms → 11ms (5,454x faster)

46 unique building files are now read, parsed, packed, and AABB-computed in parallel before the building loop even starts. By the time BuildRaymarchBlock runs, every file is already cached — each call is a zero-clone dictionary lookup.

5. Optimization #3: The Hidden GC Killer — .Clone()

This was the most impactful change — not for build time, but for runtime FPS. The voxel cache had a subtle but devastating bug: it cloned the entire voxel array on every single cache hit.

Before — .Clone() on Every Cache Hit
private static (uint[] data, ...) GetPackedVoxels(string path) { if (cache.TryGetValue(path, out var cached)) { return ((uint[])cached.data.Clone(), ...); } // ... load from disk ... cache[path] = (packedData, ...); return ((uint[])packedData.Clone(), ...); }

Every cache hit allocates a brand new array, copies all data into it, and returns the copy. The copy is used once (to upload to GPU) then becomes garbage.

After — Direct Reference (Zero Copy)
private static (uint[] data, ...) GetPackedVoxels(string path) { if (cache.TryGetValue(path, out var cached)) { return (cached.data, ...); // no clone! } // ... load from disk ... cache[path] = new CachedVoxelData { data = packedData, ... }; return (packedData, ...); // no clone! }

The cached array is returned directly. SetData() copies it to the GPU (read-only), and AABB computation only reads it. Zero allocations, zero garbage.

The Garbage Cascade — Visual

For a 500-block city with 1065 cache hits, here's what happened on every build:

Step 1 Build starts
1065 GetPackedVoxels calls
→
Step 2 1065 array allocations
~30,000-100,000 elements each
→
Step 3 SetData copies to GPU
arrays now unreferenced
→
Step 4 ~200-400 MB of dead arrays
sitting on the Large Object Heap
→
Step 5 GC triggers Gen 2 collection
STOP THE WORLD — all threads paused
→
Step 6 LOH fragmentation
heap is swiss cheese
→
Step 7 Frame stutter for 10-30 seconds
while GC cleans up
Why This Affected Runtime FPS (Not Just Build Time)

The GC did eventually clean up the garbage — but the cleanup itself was the problem:

  • Large Object Heap (LOH): Arrays >85,000 bytes go straight to Gen 2. Gen 2 collections are full stop-the-world pauses that can last hundreds of milliseconds.
  • Fragmentation: After collection, the LOH is fragmented. The GC must compact it — another expensive pause.
  • Repeated builds: Every time you changed city size or restarted, another ~200MB of garbage was dumped. The cycle never stopped.
  • Per-frame culling: The frustum culling loop iterates all chunks every frame. With a bloated heap, CPU cache misses were more frequent, slowing each frame.

The Fix — Memory Flow After Optimization

Step 1 Build starts
1065 GetPackedVoxels calls
→
Step 2 Return cached array directly
zero allocations
→
Step 3 SetData copies to GPU
cached array stays alive
→
Step 4 Zero garbage
nothing to collect
→
Step 5 No GC pauses
smooth frames immediately
→
Step 6 250-300 FPS
no stutter, no hitches
Result: 250-300 FPS (from ~60-90 FPS with stutter)

By eliminating .Clone(), we removed hundreds of MB of garbage per build. The GC has nothing to collect, so there are no pauses. The game runs smooth from the moment the city loads.

6. Optimization #4: Pre-Computed AABB

Every chunk needs a tight bounding box (AABB) for frustum culling. Previously, ComputeTightAABB() scanned every voxel in a chunk on the main thread during placement.

Before — AABB Computed Per Chunk (Main Thread)
For each chunk:
ComputeTightAABB()
scan all voxels to find min/max bounds
→
500 chunks × ~30,000 voxels each
= 15,000,000 voxel reads
After — AABB Pre-Computed in Parallel
Thread 1 Load file + compute AABB
Thread 2 Load file + compute AABB
Thread N Load file + compute AABB
→
AABB stored in cache
LoadChunkFromData uses O(1) lookup

The AABB is now computed once during parallel pre-load and stored in the CachedVoxelData struct. When LoadChunkFromData runs, it does a simple dictionary lookup instead of scanning millions of voxels.

Result: ~60,000ms → 0ms (absorbed into parallel pre-load)

AABB computation is now "free" — it happens alongside file I/O in the parallel pre-load phase. The main thread never has to scan voxels for bounds.

7. The Remaining Bottleneck: Terrain GPU Upload

After all optimizations, one bottleneck remains: Phase 1B — uploading terrain voxel data to the GPU. This is 99.6% of total build time.

1A: Terrain gen (parallel)
11ms
1B: Terrain GPU upload
6,000ms
2A: File pre-load (parallel)
11ms
2B: Building placement
50ms

Why Is GPU Upload So Slow?

Each terrain chunk requires:

1
ComputeBuffer allocation
GPU memory request
2
SetData() call
CPU → GPU transfer
3
GameObject creation
scene hierarchy overhead

For 500 chunks, that's 500 separate GPU buffer allocations. The super-linear scaling comes from GPU memory pressure — as more buffers accumulate, the driver has to work harder to manage them.

City Size Chunks Per-Chunk Cost Total Time Scaling
100 blocks 100 ~60ms/chunk 6,000ms baseline
500 blocks 500 ~247ms/chunk 123,500ms 4.1x cost for 5x chunks
Next Step: Terrain Batching

Instead of 500 separate ComputeBuffer allocations, combine all terrain chunks into 1-4 large buffers. This would cut the upload loop from 500 iterations to ~4, eliminating the GPU memory pressure that causes super-linear scaling.

Expected result: 500-block terrain upload from ~124,000ms → ~500ms (estimated).
