1 Overview — The Two Optimizations

Two seemingly unrelated fixes, same core principle: do the work once, reuse the result.

TRS Matrix Cache

What: Pre-compute the position/rotation/scale matrices for all 984 buildings at load time instead of rebuilding them every frame.

Impact: Eliminates 984 Matrix4x4.TRS() calls + 10 array allocations per frame → zero per-frame cost.

Where: VoxelChunkManager.cs — RegisterSector() + RenderBakedSectors()

Collision World Flat Array

What: Replace Dictionary<Vector3Int, byte> with a flat byte[] array for voxel collision data.

Impact: 78s → 371ms load time (211× faster) — eliminates 13.9M dictionary hash computations.

Where: VoxelCollisionWorld.cs — RegisterTerrainChunk()

Imagine a restaurant kitchen:

TRS cache is like pre-chopping all your vegetables before service starts, instead of chopping each one to order. The vegetables don't change between orders, so why re-chop them 60 times per second?

Flat array is like replacing a filing cabinet (where you search by name, hash the name, find the folder, open it) with a numbered shelf — "ingredient #4,523 is on shelf 4,523." No searching, no hashing, just direct access.

2 What Is a TRS Matrix?

TRS = Translation, Rotation, Scale — packed into a single 4×4 matrix the GPU uses to place an object in 3D space.

When the GPU draws a building, it needs three pieces of information:

📍 Translation (T)

Where is the building in world space?

(x=15.2, y=0, z=-8.4)

🔄 Rotation (R)

Which way is it facing?

Quaternion.identity (no rotation — all our buildings are axis-aligned)

📐 Scale (S)

How big is it?

(12 × 20 × 12 voxels) × 0.05m = 0.6m × 1.0m × 0.6m

The 4×4 Matrix Structure

Matrix4x4.TRS(position, rotation, scale) packs all three into a single 4×4 matrix. The GPU reads this matrix in the vertex shader to transform each vertex from "proxy cube space" into world space:

Why a matrix?

The GPU can multiply a vertex position by this single matrix in one operation: worldPos = TRS × localPos. Without it, the GPU would need separate translation, rotation, and scale steps for every vertex of every building. One matrix = one multiply = maximum efficiency.

3 The Problem: Rebuilding 984 Matrices Every Frame

Before Phase 1, RenderBakedSectors() rebuilt all 984 matrices from scratch — every single frame.

Every Frame (60-120× per second)
RenderBakedSectors() is called
For Each Sector (10 sectors)
Allocate new Matrix4x4[buildingCount]
For Each Building (984 total)
Read meta → compute size → compute center → Matrix4x4.TRS()
DrawMeshInstanced(matrices)
GPU draws all buildings — matrices are identical to last frame!

❌ Before Phase 1

// RenderBakedSectors — runs EVERY FRAME var matrices = new Matrix4x4[sector.buildingCount]; for (int i = 0; i < sector.buildingCount; i++) { var meta = sector.cpuMeta[i]; var pos = sector.cpuPositions[i]; int dx = (int)meta.y; int dy = (int)meta.z; int dz = (int)meta.w; float vsb = pos.w > 0f ? pos.w : sector.voxelSize; var buildingSize = new Vector3(dx, dy, dz) * vsb; var paddedSize = buildingSize + new Vector3(vsb, vsb, vsb); var centerPos = new Vector3(pos.x, pos.y, pos.z) + paddedSize * 0.5f; matrices[i] = Matrix4x4.TRS(centerPos, Quaternion.identity, paddedSize); } cmd.DrawMeshInstanced(..., matrices, ...);

Result changes between frames?No — so don't recompute!
The key insight

Buildings are static. They don't move, rotate, or change size. The TRS matrix for building #500 is identical on frame 1 and frame 100,000. Rebuilding it every frame is pure waste — like recalculating 2+2=4 sixty times per second.

4 The Fix: Cache Once, Reuse Forever

Move the matrix computation from RenderBakedSectors() (per-frame) to RegisterSector() (once at load).

RegisterSector() — called once per sector at load
Building data arrives: meta, positions, voxel size
BuildSectorMatrices()
Loop through all buildings, compute TRS once, store in cachedMatrices
RenderBakedSectors() — every frame
Just read sector.cachedMatrices — no computation needed
DrawMeshInstanced(cachedMatrices)
GPU draws all buildings with pre-built matrices

What changed in the code

Added to BakedSector class

public Matrix4x4[] cachedMatrices; // Pre-built TRS matrices // (buildings never move)

Added BuildSectorMatrices() helper

private static Matrix4x4[] BuildSectorMatrices( Vector4[] meta, Vector4[] positions, int count, float voxelSize) { var matrices = new Matrix4x4[count]; for (int i = 0; i < count; i++) { // ... same TRS logic, but // only runs ONCE ... matrices[i] = Matrix4x4.TRS(...); } return matrices; }

Why this matters at scale

At 100 blocks, saving 0.1ms per frame is nice. At 500 blocks (4,920 buildings), the per-frame matrix rebuild would cost 5-10ms — enough to drop you from 120fps to 60fps. The cache eliminates this entirely, making the rendering cost O(1) regardless of city size.

5 Collision World — Dictionary vs Flat Array

The 78-second load time bottleneck was not terrain generation or GPU upload — it was Dictionary<Vector3Int, byte> doing 13.9 million inserts.

The Problem: Dictionary Hashing

Every voxel in the terrain collision world was stored as a key-value pair in a Dictionary<Vector3Int, byte>. For a 100-block city, that's 13.9 million entries. Each insert requires:

1. Hash the Vector3Int key
XOR of x, y, z coordinates → hash code
2. Find the bucket
hash % bucketCount → probe the bucket array
3. Handle collisions
If bucket occupied, walk the collision chain
4. Internal resize (~24 times)
Dictionary doubles capacity, re-hashes ALL existing entries

❌ Dictionary<Vector3Int, byte>

// Each voxel insert: collisionDict[new Vector3Int(x, y, z)] = value; // Internally: // 1. Compute hash = x ^ y ^ z // 2. bucket = hash % buckets.Length // 3. Walk collision chain // 4. If full → resize (copy ALL entries) // This happens ~24 times growing to 13.9M
Operations13.9M inserts
Hash computations13.9M+
Internal resizes~24 (each copies all entries)
Memory overhead~500MB+ (entry structs + buckets)
Load time78,466ms

✅ Flat byte[] Array

// Each voxel insert: collisionArray[idx] = value; // Internally: // 1. idx = x * strideY * strideZ // + y * strideZ // + z // 2. array[idx] = value ← that's it. // No hashing. No buckets. // No collision chains. No resizes // (except ~10 Array.Copy grows).
Operations13.9M array writes
Hash computations0
Internal resizes~10 (fast Array.Copy)
Memory overhead13.3MB (just the bytes)
Load time371ms

6 The "All Directions" Grid Expansion Bug

Switching to a flat array introduced a new problem: the city isn't laid out from a corner — chunks exist in all directions, causing negative array indices.

The Bug

When we replaced the dictionary with a flat array, we assumed the first terrain chunk (row 0, col 0) was at the most negative corner. Array indices were computed as:

// Index computation (original — buggy) int idx = (offX - originX) * strideY * strideZ + (offY - originY) * strideZ + (offZ - originZ); // If offZ < originZ → negative index → CRASH

What happened

The first chunk (r0c0) was registered at some position, setting the grid origin. But chunks further south had more negative Z values than the origin, producing negative indices:

Imagine a chess board that can grow:

You start with an 8×8 board and place a piece at square E4. Then someone wants to place a piece at "A-3" — a square that doesn't exist because it's south of the board's edge. Instead of crashing, you attach a new row of squares to the south edge, shift your coordinate system so A-3 is now valid, and copy the existing board into the right position in the new larger board. That's exactly what the grid expansion does.

7 How the Two Fixes Compound

Both optimizations follow the same principle — but they target different parts of the pipeline.

Collision World (Load Time)

When: Once, at city load

What it eliminates: 13.9M dictionary hash computations + 24 internal resizes

Impact: 78s → 371ms (211× faster load)

TRS Cache (Per Frame)

When: Every frame, 120× per second

What it eliminates: 984 matrix builds + 10 array allocations

Impact: ~0.1ms/frame saved (scales to 5-10ms at 500 blocks)

The Compound Timeline

78,466ms
Dictionary collision world + per-frame TRS rebuild
13.9M dictionary inserts dominate load time. Every frame rebuilds 984 matrices.
~371ms
Flat array collision world (fix 1)
Load time drops 211×. But per-frame TRS rebuild still wastes CPU every frame.
~371ms + 0ms/frame
Flat array + TRS cache (both fixes)
Fast load AND zero per-frame matrix waste. Both CPU and GPU headroom maximized.
The shared principle

Both fixes identify work that produces the same result every time and move it from "repeat constantly" to "do once." The collision grid doesn't change after load. The TRS matrices don't change after registration. Recognizing invariant computation is the most powerful optimization technique in real-time rendering.

How to measure an optimization

Before: Note the avg frame time (e.g. 8.41ms). After: Check if avg dropped (e.g. 7.92ms). The difference (0.49ms) is the real gain — regardless of what FPS shows. vSync stays on, the game stays smooth, and you still get accurate measurements.
