## 1. Overview

### The Problem

Our voxel characters (Vinny, hoods, pedestrians) are **raymarched voxel volumes** — not polygonal meshes with skeletal rigs. Traditional Unity animation (Animator, skinned meshes, bone hierarchies) does not apply. Currently, each character is a single rigid volume that slides across the ground with a yaw rotation. No limb movement, no articulation.

### The Solution: Voxel Groups

Tag each voxel with a `groupID` (head, torso, left arm, right arm, left leg, right leg). The raymarch shader applies **independent procedural transforms per group** — rotations around group-specific pivot points (shoulder for arms, hip for legs, neck for head). The motion is generated by shader math (sin waves, rotation matrices) driven by `animTime`, not pre-baked keyframe clips.

**This is procedural animation with articulation** — not the RimWorld-style whole-body bob, but real per-limb movement computed on the GPU inside the DDA raymarch loop.

### What This Enables

- **Walking with arm/leg swing** — NPCs stroll naturally, limbs counter-swinging
- **Head look-around** — pedestrians stop and turn heads (Gangsters-inspired suspicious vibe)
- **Hood "coast clear" check** — same head-turn, triggered by crime AI
- **Aiming arms** — raise arm to fire from cover
- **Crouching** — compress legs and lower torso for cover
- **Flinch/recoil** — per-limb reaction to hits and firing

### Why Not the Other Techniques?

| Technique | Why Not Sufficient Alone |
|---|---|
| Procedural shader (whole-body) | RimWorld feel — no limb articulation, can't aim arms or swing legs |
| Voxel swap (stop-motion) | Choppy, no interpolation, memory-heavy for many poses |
| Morph targets | Still whole-body, topology must match, no per-limb control |
| **Voxel groups** ✅ | Real articulation, GPU-driven, smooth, per-limb control |

**Recommended hybrid**: Procedural (Technique 1) for 50+ ambient NPCs (cheap), voxel groups (Technique 3) for 4-20 combat participants (articulated). Voxel swap (Technique 2) supplements for death poses.

## 2. Design Reference: Gangsters-Inspired Behavior

### Source Inspiration

The original *Gangsters* game (1998, Eidos Interactive) had all pedestrians walking around and randomly stopping to look around by turning their heads. This made everyone look suspicious — you couldn't tell if someone was a civilian going about their day or a hood checking if the coast was clear before committing a crime. This blended perfectly into the criminal gameplay.

### Three Animation States

1. **Walking with limb swing** — ambient NPCs stroll through the city with natural arm/leg counter-swing. Not robotic, not RimWorld-style whole-body bob. Limbs move independently. Looks alive.

2. **Random head look-around** — pedestrians stop, turn head left, pause, turn right, then resume walking. Just like Gangsters. Makes everyone look slightly suspicious even when innocent.

3. **Hood "coast clear" check** — same head-turn animation but triggered by crime AI: hood pauses at a corner, looks both ways (head tracks left → right), then either proceeds with the crime or backs off if a cop is visible.

### The "Suspicious Blend"

The key insight is that the suspicious atmosphere is **emergent** — innocent pedestrians and criminal hoods use the *same* head-turn animation, so you can't tell them apart until the hood actually does something. This is the Gangsters feel, and it requires no special "suspicious" animation — just the same look-around behavior triggered by different AI logic.

### Animation State Mapping

All states use the same voxel group system — same shader path, same instance buffer, different `animState` values:

```
IDLE        → breathing (subtle torso scale), no limb movement
WALKING     → legs swing, arms counter-swing, slight body bob
LOOKING     → body stops, head rotates (procedural yaw offset on head group)
CHECKING    → same as LOOKING but triggered by crime AI, longer pause
AIMING      → right arm raises to firing position, head tracks target
CROUCHING   → legs compress, torso lowers, arms tuck
FLINCHING   → brief backward offset + arm recoil
FALLING     → whole-body rotation (can use procedural or voxel swap)
DOWN        → static fallen pose (voxel swap to death pose)
```

## 3. Current Architecture (What We Have)

### Instance Buffer (CPU → GPU)

Currently, each instanced character sends `float4(x, y, z, yaw)` = 16 bytes per instance:

```
VoxelChunkManager.RenderInstancedGroup():
    offsets[writeIdx] = new Vector4(ic.worldOffset.x, ic.worldOffset.y, ic.worldOffset.z, ic.yaw);
    → ComputeBuffer<float4> _InstanceOffsets
```

### Shader (GPU)

In `VoxelProxyRaymarch.shader`, the vertex shader reads per-instance data:

```hlsl
StructuredBuffer<float4> _InstanceOffsets;

// In vert():
float4 instData = _InstanceOffsets[unity_InstanceID];
output.volumeOffset = instData.xyz;  // world position
output.yaw = instData.w;             // yaw rotation
```

The fragment shader raymarches the entire volume with one yaw rotation. All voxels rotate together as a rigid block. No per-group transforms exist.

### Voxel Data

Each voxel is a `uint` packed value storing a material index. The voxel buffer is shared across all instances of the same `.stasset` (one copy in GPU memory, referenced by all instances). No group ID information is stored.

### Key Files

| File | Role |
|---|---|
| `VoxelProxyRaymarch.shader` | Raymarch shader — renders voxel volumes via proxy cube |
| `VoxelChunkManager.cs` | Manages instanced rendering, buffers, draw calls |
| `VoxelCharacter.cs` | Per-character component (position, yaw, collision) |
| `.stasset` files | Voxel data (MagicaVoxel → custom format) |

## 4. Target Architecture (What We Need)

### Voxel Group IDs

Each voxel in the character model stores a `groupID` alongside its material index:

| Group ID | Name | Voxels | Pivot Point | Transform |
|---|---|---|---|---|
| 0 | Body/Torso | torso + pelvis | center | identity (no per-group transform) |
| 1 | Head | head + neck | neck base | yaw + pitch offset (head tracking) |
| 2 | Left Arm | left shoulder → hand | left shoulder | swing rotation (walk) / raise (aim) |
| 3 | Right Arm | right shoulder → hand | right shoulder | swing rotation (walk) / raise (aim) |
| 4 | Left Leg | left hip → foot | left hip | stride rotation (walk) |
| 5 | Right Leg | right hip → foot | right hip | stride rotation (walk) |

**Storage**: The groupID can be stored two ways:
- **Option A**: Parallel `uint[]` buffer (same size as voxel buffer, 1 groupID per voxel). Simple, no changes to existing voxel data format.
- **Option B**: Pack groupID into high bits of existing voxel `uint` (if material index doesn't use all 32 bits). Saves a buffer but couples data formats.

**Recommendation**: Option A (parallel buffer) — cleaner separation, no risk of breaking existing voxel loading.

### Expanded Instance Buffer

```
Phase 0 (current):  float4(x, y, z, yaw)                        — 16 bytes
Phase 1 (anim):     float4(x, y, z, yaw) + float4(animState,    — 32 bytes
                                animTime, speed, 0)
Phase 2 (combat):   + float4(faction, health, targetYaw, 0)     — 48 bytes
Phase 3 (groups):   + float4 groupPivot[6] (optional, if        — up to 144 bytes
                                pivot points aren't hardcoded)
```

**Backward compatibility**: Unused fields are zeroed. Characters without group IDs render normally (all voxels in group 0 = identity transform). The shader checks if `_GroupIDs` buffer is bound — if not, falls back to rigid volume rendering.

### Shader Data Flow

```
CPU per frame:
  1. Update InstancedCharacter.animState, animTime
  2. Write float4[] to _InstanceOffsets buffer (now 2x float4 per instance)
  3. Bind _GroupIDs buffer (per InstancedGroup, uploaded once at load)

GPU vertex shader:
  1. Read _InstanceOffsets[instanceID] → position, yaw
  2. Read _InstanceOffsets[instanceID + count] → animState, animTime
  3. Pass to fragment shader via Varyings

GPU fragment shader (raymarch loop):
  1. Transform ray into volume-local space (existing yaw rotation)
  2. DDA march through voxels
  3. For each DDA voxel: read groupID = _GroupIDs[voxelIndex]
  4. If groupID > 0: compute INVERSE group transform (posedPos → restPos)
  5. Sample _VoxelData at rest position (not DDA position)
  6. If hit: use DDA position for lighting + depth (no output offset)
```

### Step 4: Add Group Transforms to the Shader (GPU side)

**Goal**: Apply per-group rotations inside the DDA raymarch loop.

**Files**: `VoxelProxyRaymarch.shader`

**Changes**:

1. Add new bindings:
```hlsl
StructuredBuffer<uint> _GroupIDs;  // groupID per voxel (0 = no transform)
```

2. Expand Varyings to carry anim data:
```hlsl
struct Varyings
{
    // ... existing fields ...
    float animState;
    float animTime;
    float animSpeed;
};
```

3. In vertex shader, read second float4 from instance buffer:
```hlsl
#ifndef BUILDING_INSTANCING
    float4 instData = _InstanceOffsets[unity_InstanceID];
    output.volumeOffset = instData.xyz;
    output.yaw = instData.w;
    // NEW: read anim data from second half of buffer
    float4 animData = _InstanceOffsets[unity_InstanceID + _InstanceCount];
    output.animState = animData.x;
    output.animTime = animData.y;
    output.animSpeed = animData.z;
#endif
```

4. In fragment shader, inside the DDA loop when a voxel is hit:
```hlsl
// After: uint packed = _VoxelData[bufferOffset + VoxelIndex(voxel, dims)];
// After: if (mat != 0u) {

uint groupID = 0;
if (_GroupIDsEnabled) {
    groupID = _GroupIDs[bufferOffset + VoxelIndex(voxel, dims)];
}

// Compute per-group transform
float3 groupOffset = float3(0, 0, 0);
float3x3 groupRot = float3x3(1, 0, 0, 0, 1, 0, 0, 0, 1);

if (groupID > 0u) {
    float3 voxelLocalPos = float3(voxel) * voxelSize;
    float3 pivot = _GroupPivots[groupID];  // hardcoded or from buffer
    float3 relPos = voxelLocalPos - pivot;

    if (groupID == 1u) { // Head
        float headYaw = sin(input.animTime * 2.0) * 0.5;
        float c = cos(headYaw), s = sin(headYaw);
        groupRot = float3x3(c, 0, -s, 0, 1, 0, s, 0, c);
    }
    else if (groupID == 2u) { // Left arm
        float swing = sin(input.animTime * 6.0 * input.animSpeed) * 0.3;
        float c = cos(swing), s = sin(swing);
        groupRot = float3x3(1, 0, 0, 0, c, -s, 0, s, c);
    }
    else if (groupID == 3u) { // Right arm
        float swing = sin(input.animTime * 6.0 * input.animSpeed + 3.14159) * 0.3;
        float c = cos(swing), s = sin(swing);
        groupRot = float3x3(1, 0, 0, 0, c, -s, 0, s, c);
    }
    else if (groupID == 4u) { // Left leg
        float stride = sin(input.animTime * 6.0 * input.animSpeed + 3.14159) * 0.4;
        float c = cos(stride), s = sin(stride);
        groupRot = float3x3(1, 0, 0, 0, c, -s, 0, s, c);
    }
    else if (groupID == 5u) { // Right leg
        float stride = sin(input.animTime * 6.0 * input.animSpeed) * 0.4;
        float c = cos(stride), s = sin(stride);
        groupRot = float3x3(1, 0, 0, 0, c, -s, 0, s, c);
    }

    // Apply transform: rotate relPos around pivot, then translate back
    float3 transformedPos = mul(groupRot, relPos) + pivot;
    // Use transformedPos for depth + lighting calculations
}
```

**Key insight**: The group transform is applied *inside the DDA loop* when a voxel is hit. The voxel's local position is offset by its group's rotation around the group's pivot point. The raymarch still works — it just hits voxels at slightly different positions because the group rotation moves them.

**Challenge**: The DDA loop marches through *voxel grid space* (integer coordinates). The group transform displaces where the voxel *appears* in world space, but the DDA still needs to find it at its *grid* position. Two approaches:

- **Approach A (simpler)**: Apply group transform only to the *output* (depth + normal + color), not to the raymarch itself. The voxel is found at its grid position, but its rendered position is offset. This can cause slight visual artifacts at group boundaries but is much simpler.

- **Approach B (correct)**: Transform the ray into per-group local space before testing each voxel. More complex but visually correct. Requires checking if the ray passes through a group's transformed bounding box.

**Recommendation**: Start with Approach A. If visual artifacts are unacceptable at group boundaries, upgrade to Approach B.

**Effort**: 4-8 hours (Approach A) or 1-2 days (Approach B)

### Step 5: Drive Animation State from C# (CPU side)

**Goal**: Update `animTime` each frame and set `animState` based on behavior.

**Files**: `VoxelCharacter.cs` or new `CharacterAnimation.cs`

**Changes**:

```csharp
public enum AnimState : int
{
    Idle = 0,
    Walking = 1,
    Looking = 2,
    Checking = 3,
    Aiming = 4,
    Crouching = 5,
    Flinching = 6,
    Falling = 7,
    Down = 8
}

public class CharacterAnimation : MonoBehaviour
{
    public VoxelCharacter voxelChar;
    public AnimState currentState = AnimState.Idle;
    public float walkSpeed = 1.0f;

    private float animTime = 0f;

    void Update()
    {
        animTime += Time.deltaTime;

        if (instancedHandle != null)
        {
            instancedHandle.animState = (float)currentState;
            instancedHandle.animTime = animTime;
            instancedHandle.animSpeed = walkSpeed;
        }
    }

    public void SetState(AnimState newState)
    {
        if (currentState != newState)
        {
            currentState = newState;
            animTime = 0f; // reset clock on state change
        }
    }
}
```

**Effort**: 1-2 hours

```
Phase 0 (current):  float4(x, y, z, yaw)                        — 16 bytes/instance
Phase 1 (anim):     float4(x, y, z, yaw) + float4(animState,    — 32 bytes/instance
                                animTime, speed, 0)
```

**Memory impact at 500 instances**:
- Phase 0: 500 × 16 = 8 KB
- Phase 1: 500 × 32 = 16 KB
- Phase 2: 500 × 48 = 24 KB
- Phase 3: 500 × 144 = 72 KB (worst case, unlikely — most chars don't need per-instance pivots)

All well within GPU memory budget. The shared voxel buffer (typically 50-200 KB per character model) is uploaded once and shared across all instances.

## 7. Group Pivot Points

Each group rotates around a pivot point defined in voxel-local space (origin = volume corner, units = voxels). These are hardcoded in the shader or stored as constants per character model.

**Pivot points are model-specific** — they depend on how Vinny is proportioned. The values below are estimates for a typical humanoid voxel model. They must be calibrated once the actual model dimensions are known.

```
Group 0 (Torso):   No pivot (identity transform)
Group 1 (Head):    pivot = (dimX/2, neckY, dimZ/2)     — neck base
Group 2 (L Arm):   pivot = (shoulderX_L, shoulderY, dimZ/2) — left shoulder
Group 3 (R Arm):   pivot = (shoulderX_R, shoulderY, dimZ/2) — right shoulder
Group 4 (L Leg):   pivot = (hipX_L, hipY, dimZ/2)      — left hip
Group 5 (R Leg):   pivot = (hipX_R, hipY, dimZ/2)      — right hip
```

**Example for a 20×40×20 voxel character**:
```
Head pivot:    (10, 32, 10)   — neck at 80% height
L Arm pivot:   (5,  30, 10)   — left shoulder at 75% height, 25% width
R Arm pivot:   (15, 30, 10)   — right shoulder at 75% height, 75% width
L Leg pivot:   (7,  20, 10)   — left hip at 50% height
R Leg pivot:   (13, 20, 10)   — right hip at 50% height
```

**Calibration process**: Once Vinny's model is loaded with group IDs, run a debug view that renders pivot points as small colored markers. Adjust until rotations look natural.

## 10. Risks and Mitigations

### Risk: Group Boundary Artifacts (Approach A — RESOLVED)

**Problem**: When using Approach A (transform output only, not raymarch), voxels at group boundaries may appear to "tear" or overlap during large rotations. Additionally, Approach A was **completely invisible** — the output offset only changed the depth buffer, not screen position or color.

**Resolution**: Upgraded to Approach B (inverse-transform sampling). DDA now samples voxel data at rest positions, so limbs appear at their posed positions on screen. No boundary artifacts observed with moderate rotation amplitudes.

### Risk: Shader Complexity

**Problem**: Per-voxel group transform adds branchy code inside the DDA loop, which is already the hottest path in the shader.

**Mitigation**:
- Group ID lookup is a single buffer read (same as material lookup)
- The `if (groupID > 0u)` branch is coherent — most voxels in a hit are in the same group
- Benchmark early; if > 3ms impact, consider pre-computing transforms per-group (6 transforms) instead of per-voxel

### Risk: Model Re-authoring

**Problem**: Vinny's `.stasset` may not have group metadata. Re-authoring could be time-consuming.

**Mitigation**:
- Programmatic partitioning by Y-slice and X-slice (Step 1 heuristics)
- Can be done as a post-process script, no manual MagicaVoxel work needed
- Test with a simple blocky test figure first (6 colored boxes as body parts)

### Risk: Pivot Point Calibration

**Problem**: Pivot points are model-specific and must be tuned by eye.

**Mitigation**:
- Debug visualization mode (render pivots as markers)
- Start with estimated values, iterate
