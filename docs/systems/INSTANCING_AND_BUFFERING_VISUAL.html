1 What is a Draw Call?

Every time the CPU tells the GPU "draw this mesh with this material," that's a draw call. The GPU is fast — the CPU is the bottleneck.

Imagine a restaurant kitchen:

The GPU is the chef — it can cook 1000 burgers instantly. But the waiter (CPU) has to write down each order individually, walk to the kitchen, and read it out. If the waiter writes 1600 separate tickets, the chef stands around waiting. Instancing is like handing the chef a single ticket that says "make 1600 burgers, here's the list of toppings for each one."

2 What is a ComputeBuffer?

A block of GPU memory that the CPU fills once and the GPU reads many times. Think of it as an array that lives on the GPU.

Imagine a shipping manifest:

Instead of telling each worker individually "you're at position (3,0,5), you're at position (7,0,12)..." — you pin a manifest to the wall (GPU memory) with everyone's position. Each worker reads their own row. The foreman (CPU) only has to pin the manifest once.

// CPU side — create the buffer once ComputeBuffer instanceBuffer = new ComputeBuffer(1600, Marshal.SizeOf<InstanceData>()); // Fill with per-building data InstanceData[] data = new InstanceData[1600]; for (int i = 0; i < 1600; i++) { data[i].position = blocks[i].worldPos; data[i].rotation = blocks[i].rotationY; data[i].color = blocks[i].tintColor; } instanceBuffer.SetData(data); // GPU reads it in the shader // cbuffer InstanceData { float3 position; float rotation; float4 color; }

3 The Shared-Material Bug (Invisible Vinny)

The #1 instancing pitfall. When multiple instanced groups share a material but need different buffer bindings, the last one wins. Everyone else goes invisible.

🐛 The Story of Invisible Vinny

Vinny (the NPC character) and a civilian car both used instanced rendering through the same proxyMaterial. Each had its own voxel buffer with different dims and voxel sizes. What went wrong?

1
Vinny's group registers first. The character instancer sets proxyMaterial._VoxelData = characterBuffer, _VoxelSize = 0.02, then records DrawMeshInstanced into the command buffer.
proxyMaterial._VoxelData = characterBuffer → cmd.DrawMeshInstanced(character) ← recorded, not executed yet
2
Car group registers next. The vehicle instancer sets proxyMaterial._VoxelData = carBuffer, _VoxelSize = 0.05, then records its DrawMeshInstanced.
proxyMaterial._VoxelData = carBuffer ← OVERWRITES Vinny's binding → cmd.DrawMeshInstanced(car)
3
Command buffer executes: Vinny is invisible! Both draw calls run with _VoxelData = carBuffer (the last value set). Vinny's raymarch reads car voxels at car voxelSize (0.05) with car dims — the character's actual voxels (at 0.02 spacing) are never hit → discard → invisible.
GPU runs both draws with carBuffer → character raymarch misses → invisible Vinny
4
The fix: MaterialPropertyBlock. Each instanced group gets its own MaterialPropertyBlock passed to DrawMeshInstanced. The shared proxyMaterial is never mutated — each draw call carries its own buffer/dims/voxelSize snapshot.
Character MPB → characterBuffer, 0.02 | Car MPB → carBuffer, 0.05 → no conflict ✅

Key Lesson: Any time multiple draw calls share a material but need different buffer bindings, use MaterialPropertyBlock. It's a per-draw-call override that doesn't mutate the shared material. Think of it as a sticky note attached to a specific draw call — it doesn't change the original document.

4 Shader-Side Instancing

The GPU shader reads per-instance data from the buffer and offsets each vertex. Here's how it flows:

Vertex Input (Base Mesh)
e.g. building corner at (1.5, 0, 1.5) — same for ALL instances
Read Instance Buffer[instance_ID]
Gets position, rotation, scale, color for THIS specific building
Offset + Rotate Vertex
vertex.pos += instance.position; vertex.pos = rotate(vertex.pos, instance.rotation)
Apply Per-Instance Color
fragment.color *= instance.tintColor
Output to Screen
This building is now at its correct world position with its unique tint

Shader Code (Simplified)

// --- GPU shader (HLSL / Unity ShaderLab) --- // Per-instance data — comes from ComputeBuffer struct InstanceData { float3 position; float rotation; float4 color; }; // Unity auto-fills this with the instance index UNITY_INSTANCING_BUFFER_START(Props) UNITY_DEFINE_INSTANCED_PROP(InstanceData, _InstanceData) UNITY_INSTANCING_BUFFER_END(Props) float4 vert(appdata_t IN, uint instanceID : SV_InstanceID) : SV_Position { // Read THIS instance's data from the buffer InstanceData inst = UNITY_ACCESS_INSTANCED_PROP(Props, _InstanceData); // Offset the base mesh vertex to world position float3 worldPos = IN.vertex.xyz + inst.position; worldPos = rotateY(worldPos, inst.rotation); // Pass tint to fragment shader IN.color = inst.color; return UnityObjectToClipPos(float4(worldPos, 1.0)); }

5 Rendering Tiers

Not everything should be instanced. Steel City uses three tiers depending on how dynamic an object is:

TIER 1
BAKE
Sector Baking (Static)
All static buildings in a sector are combined into a single mesh. One draw call for the entire sector. No per-frame updates needed.
📦 Example: 200 buildings in a city block → 1 baked mesh → 1 draw call
TIER 2
INSTANCE
GPU Instancing (Batched Dynamic)
Many copies of the same mesh with different transforms. ComputeBuffer holds per-instance data. One draw call for all copies.
📦 Example: 50 NPCs walking around → 1 instanced draw call (50 entries in buffer)
TIER 3
INDIVIDUAL
Individual Draw (Unique Mutation)
When an object needs unique per-vertex state (damage, color change, animation). One draw call per object. Most expensive but most flexible.
📦 Example: A building being destroyed → needs its own mesh + draw call
Decision checklist: Can it be baked and forgotten? → Tier 1. Same mesh, different positions? → Tier 2. Unique per-vertex state? → Tier 3.

6 Sector Baking vs Instanced Characters

Two different instancing strategies for two different problems. Same pattern, different scale.

🏢 Sector Baking (Buildings)

Problem: 1600 static buildings, never move, never change.

Solution: Combine all building meshes in a sector into one giant mesh. Upload once. Forget about it.

200 buildings
Individual voxel meshes
Bake into 1 mesh
Combine vertices, translate positions
1 draw call
Forever. No per-frame cost.

Trade-off: Can't move or modify individual buildings without re-baking the whole sector.

🚶 Instanced Characters (NPCs)

Problem: 50 NPCs, same mesh, but they move every frame.

Solution: One mesh, ComputeBuffer with 50 entries. Update buffer positions every frame. Still 1 draw call.

50 NPCs
Same body mesh, different positions
Update buffer
Write 50 new positions each frame
1 draw call
Every frame, but still just 1 call

Trade-off: Must update buffer every frame (cheap — just 50 floats).

  • No LOD — all buildings render at full detail regardless of distance

9 Quick Glossary

Draw Call

CPU → GPU command: "draw this mesh with this material." Expensive because of CPU state setup, not GPU rendering.

ComputeBuffer

GPU memory block filled by CPU, read by GPU shaders. Holds per-instance data (positions, rotations, colors).

MaterialPropertyBlock

Per-draw-call material override. Prevents multiple instancers from clobbering each other's buffer bindings on a shared material.

Instancing

Rendering N copies of the same mesh in 1 draw call. GPU reads per-instance data from a buffer to place each copy.

Sector Baking

Pre-combining static meshes into one giant mesh per sector. Zero per-frame cost, but can't modify individual objects.

SV_InstanceID

GPU semantic that tells the shader which instance index it's processing. Used to look up the correct row in the instance buffer.
